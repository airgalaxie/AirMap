# AirMap — based on Dynmap®

AirMap is an independent project based on the [Dynmap®
project](https://github.com/webbukkit/dynmap), incorporating work from
[JLyne's fork](https://github.com/JLyne/dynmap) and
[airgalaxie/dynmap-paper](https://github.com/airgalaxie/dynmap-paper).
Dynmap® is the original project and remains the foundation of AirMap.
AirMap shares a hardened Dynmap core between its Paper plugin and Fabric
mod.

> [!IMPORTANT]
> AirMap is not an official Dynmap release and is not
> affiliated with, endorsed by, or supported by the Dynmap project.
> Support for AirMap and its modifications is the responsibility of the
> AirMap project and its maintainers, not the Dynmap project or its
> maintainers.

> [!NOTE]
> The authoritative product, Minecraft, platform, Java, plugin and
> dependency versions are defined in
> [`gradle/libs.versions.toml`](gradle/libs.versions.toml). Use the checked-in
> Gradle wrapper. `javaBuild` selects the build JDK, while `javaTarget`
> independently selects the generated bytecode target.

## Project scope compared with the legacy branch

| Legacy branch | Current project |
|:--|:--|
| Main configuration and render definitions stored as `.txt` files | YAML configuration, with existing `.txt` configuration files still accepted |
| Primarily bundled render definitions | Minecraft client resources supply current vanilla models and textures |
| One Java catalog setting used for the toolchain target | Separate catalog settings for the build JDK and generated bytecode target |
| Original world-name compatibility model | Canonical registry IDs, legacy aliases and separate storage-safe IDs |

------------------------------------------------------------------------

## Main changes in this fork

- **Paper and Fabric support:** Both platform artifacts use the shared
  core. The Paper adapter preserves Bukkit/Dynmap integration points where
  practical; Fabric uses its own platform adapter.
- **Central build configuration:** Platform, toolchain and dependency
  versions are selected in the version catalog.
- **Minecraft resources:** Current vanilla block states, models and
  textures are read from Minecraft client resources. Existing text-based
  configuration files remain supported.
- **Rendering compatibility:** Palette data accepts both the legacy
  `Name`/`Properties` form and the current `id`/`properties` form. Tint
  handling distinguishes biome-tinted, constant-color and untinted leaves.
- **Adaptive rendering performance:** AirMap can adjust renderer throughput at
  runtime through measured capacity experiments in the shared Core. Fullrender
  and updates share adaptive worker limits; tick health, CPU, heap and GC signals
  guide tuning and safety. Profiles select how long experiments are measured.
- **Web and storage maintenance:** Bundled web assets and SQL storage paths
  have been updated while preserving the external-server workflow.

------------------------------------------------------------------------

Other changes include removal of browser-to-server web chat and web login,
replacement of the legacy internal webserver with a small static server,
storage-backed endpoints for SQL storage, and removal of obsolete
integrations and workarounds. PostgreSQL and S3 storage are no longer
included. File-tree, SQLite, MySQL, MariaDB and Microsoft SQL Server storage
implementations remain in the core.

## Configuration and Platform Notes

-   **Configuration:** AirMap's configuration is primarily managed
    through `configuration.yaml` and related YAML files in the platform data
    folder. Existing `.txt` configuration files remain supported. General
    upstream configuration guidance still applies, with
    the canonical world-ID and storage-migration differences documented
    below.
-   **Minecraft client resources:** AirMap uses Minecraft client resources
    for current Vanilla models and textures. New installations contain
    `accept-minecraft-client-download: false`; setting it to `true` permits
    AirMap to download the resources required by this build from the official
    Mojang/Microsoft source. Existing configuration files are not
    automatically extended with new options, so operators upgrading an older
    installation must explicitly add the key when a download is needed. A
    missing key means that download permission has not been granted. A matching
    local client resource that passes the existing validation is reused
    regardless of this setting. When the required resources are missing and no
    download permission has been granted, AirMap reports the reason and disables
    itself instead of starting with incomplete models and textures.
-   **Webserver Default:** The Dynmap webserver configuration is
    present, and the bundled default configuration follows the original
    Dynmap default with `disable-webserver: false`. Deploy the generated
    web files to an external web server (e.g., Nginx, Apache), or use
    the internal static webserver if you want Dynmap to serve the
    generated web UI itself.
-   **Platform Support:** Paper and Fabric are built as separate artifacts
    against the targets selected in the central catalog. Target changes can
    require source, mapping or API adaptations and must be verified on both
    platforms.

## Model rotation compatibility

Patch X rotation follows the right-hand rule about +X: a positive 90-degree
rotation maps +Y to +Z. The Minecraft model loader negates block-state and
static-layer X angles at the patch boundary to preserve their model orientation.
Custom patch models that compensated for the previous reversed X convention
should be checked for orientation changes. Existing render resource caches are
invalidated by the Core code change and rebuilt automatically.

## Render resource cache

AirMap stores prepared Minecraft model geometry, weighted variants and texture
registrations in a local file to avoid baking the same models on every start.
Paper and Fabric use the following defaults, including when an existing
`configuration.yaml` has no cache section:

```yaml
render-cache:
  enabled: true
  directory: render-cache
```

The directory is relative to AirMap's data folder, or can be an absolute path.
The file is `render-cache/models.bin.gz` by default, independently of map storage
(filetree or SQL). Only the current cache generation is retained. Set `enabled`
to `false` to bypass cache reads and writes; delete the cache file while AirMap
is stopped to force a rebuild. The Minecraft client download permission remains
required when the source client resources are missing.

Cache validity is checked on each load using SHA-256 identities of resource
contents, ordered resource layers, AirMap Core/API code and bundled resources,
and the block-state registry including baking-relevant properties. Changes to
Minecraft resources, mods/overrides or AirMap therefore trigger rebuilding,
including same-version content changes. Archive sources are hashed as whole
files; other providers hash their complete listed asset set. Custom providers
must enumerate all their assets or supply an equivalent content fingerprint.
The current model baker has no configuration-dependent geometry settings;
texture-pack pixel processing remains outside this cache.

The first start after a change follows the normal model-loading path and saves
a compressed snapshot through a temporary file and atomic replacement where
supported. A matching snapshot restores models and texture mappings while
initializing dynamic fluid renderers normally. Missing, corrupt or inaccessible
cache files fall back to normal loading; incomplete model loads are not cached.
The log reports hits, rebuilds and saved file size. Cache validation still reads
source data, and decoded/scaled texture pixels are not persisted, so startup
savings and disk usage depend on the installation and must be measured locally.

## AirMap-only runtime performance administration

These commands are **AirMap extensions**, not commands provided by original
Dynmap. Paper and Fabric route `/airmap` and the compatibility alias `/dynmap`
to the same implementation in `DynmapCore`/`MapManager`.

| Command | Meaning and example |
|:--|:--|
| `/airmap performance status` | Show latest TPS (or unknown/stale after 15 seconds), protection stage, controller mode, admitted workers, shared ceiling, current worker budget, TPS thresholds, pauses and runtime overrides. |
| `/airmap performance tps <slow> <critical>` | Temporarily change TPS protection, e.g. `/airmap performance tps 18 12`. Requires finite numbers with `0 < critical < slow <= 19.5`. |
| `/airmap performance parallelrendercnt <count>` | Temporarily change the shared full/update worker ceiling, e.g. `/airmap performance parallelrendercnt 4`. Accepts integers from 1 through the processor count available to the JVM. |
| `/airmap performance reset` | Remove **all** runtime overrides and restore the startup configuration behavior, including the configured worker ceiling and original TPS policy. |

All four commands require `dynmap.performance` (operators by default); the
server console is supported and omits the leading `/`. Fabric's optional
`permissions.yml` uses the unprefixed name `performance`, like its other
permissions. Invalid values and changes during shutdown are rejected without
replacing valid settings. Status remains available during shutdown. No command
writes configuration files. Overrides last until reset or renderer/server
restart. Reset uses the configuration loaded at startup; it does not reread an
edited file or discard fullrender progress or learned capacity unnecessarily.

In adaptive mode the initial TPS limits are **slow=18, critical=12**; no new
configuration keys or migration are required. They are protection thresholds,
not TPS targets:

| Protection stage | New render work |
|:--|:--|
| `NORMAL` | Normal adaptive capacity experiments within the worker and chunk ceilings. |
| `SLOW` | At most one shared worker, at most five chunk loads per tick, updates admitted at most once per second, and at least one second between fullrender batches. Waiting updates take priority over waiting fullrender work. |
| `CRITICAL` | Fullrender/radius/bulk updaterender waits; eligible update-queue tiles continue with the same one-worker, five-chunk, once-per-second budget. Zoom-out processing waits as well. |

Entering a lower stage requires TPS **below** its threshold. Recovery requires
TPS at least **0.5 above** that threshold (12.5 / 18.5 with the defaults).
Missing/non-finite TPS measurements do not trigger recovery. Existing adapter
TPS sampling determines reaction time; already admitted tiles finish normally.
“Urgent updates” here means eligible tiles from the existing update queue rather
than bulk renders: no new urgency classification or queue is introduced.
Existing tile update delays and deduplication remain in effect. The one-second
admission limit also applies to previously dequeued tiles retrying for capacity;
it is an admission rate limit, not a guaranteed tile completion time.

`parallelrendercnt` is an upper bound, not a request to keep that many workers
busy. In adaptive mode an increase allows subsequent measured experiments; it
does not immediately force higher concurrency. Fullrender and updates share the
bound across worlds. A reduction stops further admissions until existing work
fits the new budget. Executor capacity is increased before publishing a higher
limit and reduced only after old reservations drain, so parents can still join
their children. Idle executor threads may expire after 30 seconds; no additional
periodic task or separate performance controller is created.

The configured profile and controller mode are preserved. In `legacy`/`observe`
and with `render-performance-auto: false`, the worker command also applies a
shared ceiling; the TPS command enables the new TPS protection explicitly.
Without a TPS override those modes retain their original TPS policy (`CONFIG`
in status). Reset restores that policy. In legacy/observe mode the existing
controller may impose stronger fullrender/zoom-out safety pauses; these are
shown separately in status. In manual mode the TPS override replaces the old
TPS render pauses until reset. Existing explicit `/dynmap pause` requests,
world unload/shutdown handling and the adaptive heap/GC safety governor remain
authoritative. Heap/GC safety can pause **all** adaptive rendering, including
critical updates; commands cannot disable it. Individual expensive tiles or
world-data copies cannot be preempted, so the budgets do not guarantee a fixed
upper bound on their execution time. Flat and Surface rendering are unchanged.

Adapter scope: **Paper and Fabric** are the adapters included by this checkout;
both use the shared command and permission path. There is no Velocity adapter
or administrative forwarding implementation in this repository: run the
commands on the rendering backend's console/server, not on a proxy. This feature
does not add Folia support; the existing Paper adapter is not declared
Folia-compatible. No Folia/Velocity runtime compatibility is claimed. A Core
whose renderer failed initialization reports commands unavailable instead of
accessing a missing manager.

## Automatic render performance

Paper and Fabric use the same adaptive controller in the Core:

```yaml
render-performance-auto: normal
render-performance-controller: adaptive
render-performance-auto-log-changes: false
```

The controller starts with one worker and a modest data budget, sampling every
five seconds. It adjusts the existing shared full/update parallelism, update
queue rate and chunk allowance. Normal throughput optimization **never adds a
fullrender pause**. Fullrender and updates retain their shared admission bound.
`parallelrendercnt`, when positive, is the optional worker ceiling; otherwise
the available processor count is the ceiling. `maxchunkspertick` is the chunk
allowance ceiling. These are limits, not throughput or utilization targets.

During discovery, worker/data capacity grows in bounded proportional steps;
the measured data wait and update mix determine which existing control to try.
A coarse step that harms throughput or TPS is rolled back, and the remaining
interval is refined instead of repeatedly trying the same excessive load.
An increase needs useful throughput gains in **two consecutive comparable
measurement windows**, without average TPS falling by more than 0.5 from its
baseline. The gain must exceed both 3% and twice the observed relative standard
error of sample throughput above tile-completion counting noise. Regular sparse
completions are therefore not mistaken for changing load. In-flight tiles that
outlast a window retain elapsed measurement time and pending trials. Very noisy
windows do not establish a stable point.
Confirmed discovery steps can follow immediately, without an extra idle or
settling window. There is no fixed tiles/s, worker count or TPS optimization
target. Search time depends on the profile, workload and available capacity;
there is no guarantee of a global optimum or a fixed convergence time.

Once further changes stop helping, the controller **holds the proven point**.
It does not periodically retry rejected capacity just because time has elapsed.
A renewed search requires a sustained change in throughput, world-data share,
full/update mix or estimated external CPU load, or an administrative limit
change. Context changes must persist across two consistently changed windows;
an isolated player join or opposite throughput fluctuations do not restart the
search. External-load/mix changes during a trial make it inconclusive: the last
settings are restored and new trials wait three measurement windows. Rendering
continues throughout this wait. Busy CPU alone holds acceleration; it never
pauses rendering. Missing measurements do not count as healthy zeroes.

Sustained TPS deterioration relative to the proven point, or elevated heap/GC
pressure, first invites a small reduction of the relevant existing budget.
The controller waits at least two windows and tolerates transient foreign load.
Such a reduction must demonstrate sustained TPS/throughput or CPU-efficiency
benefits; an ineffective reduction is not repeated at the same TPS situation.
No normal probe-down introduces fullrender delays. Following a useful reduction,
its lower working point is retained while the extra load persists. Returning to
the remembered point requires sustained relief. Recovery from TPS/heap/GC
protection also retains that destination but starts with a small budget and
restores capacity in measured steps, rather than jumping straight to the former
load. Known recovery steps may preserve throughput with essentially unchanged
CPU instead of needing a new gain on an irrelevant budget axis. The admin
ceilings and all safety pauses remain binding during discovery and recovery.

TPS protection bounds adaptive experiments: below 18 TPS rendering is strongly
throttled; below 12 TPS fullrender waits while bounded updates continue. Above
the protection limits the controller discovers, holds or gradually recovers its
measured sustainable working point.
High CPU use alone never pauses the adaptive renderer. The separate safety governor pauses new full/update work and
zoom-out scheduling after three consecutive samples with heap use at least 97%
and reported GC time at least 15% of elapsed time. It resumes at one worker after
six samples below 88% heap and 8% GC time. Unsupported measurements remain
unknown, not zero. Existing manual pauses and world-unload behavior remain.

Metrics separate world-data acquisition wall time from the existing render/output
call. The latter still includes image calculation, PNG/other encoding, hashing,
locking and storage. Thread CPU time versus wall time gives a CPU/wait indication;
it does **not** identify storage time precisely. No renderer, image encoder, hash
or storage implementation is changed. The Paper snapshot adapter consumes the
Core's soft copy budget (0.25–4 ms, depending on the current chunk allowance);
individual copies cannot be preempted. Fabric retains its existing data retrieval
mechanism and benefits from shared admission/rate control, but does not yet
consume that per-context copy budget. This change does not establish Folia support.

Profiles `conservative`, `normal` and `aggressive` select experiment windows of
60, 30 and 15 seconds. `true` aliases `normal`. `false` disables automatic tuning
and keeps the existing manual limits and TPS pause settings.

For a staged rollout, first select `render-performance-controller: observe` and
enable decision logging. The previous automatic controller remains in charge;
adaptive proposals are labelled as unapplied and cannot establish their effect.
Then select `adaptive` and compare throughput, tick health and rollback decisions
under representative fullrender and update workloads. `legacy` selects only the
previous controller, including its CPU/TPS-based pauses. No configuration is
rewritten. The absence of the new controller key selects `adaptive`.

Runtime decisions are logged only when `render-performance-auto-log-changes` is
true. They include limits, measured throughput, data share, render/output CPU
share, TPS, JVM/environment CPU, heap and GC time. CPU outside the JVM is only
estimated from environment minus process CPU; container scope and measurement
windows may differ. Decisions also appear in the render statistics command.

Existing installations are not automatically given new configuration keys. Set
`render-performance-auto: false` if existing manual limits must remain authoritative.

AirMap also writes `configuration.default.yaml` in its data folder as a comparison
reference for the installed Paper or Fabric build. It includes the build version
and is updated at startup only when its contents change. This file is not loaded
as configuration and should not be edited. Existing `configuration.yaml` or legacy
`configuration.txt` settings remain untouched; compare them with the reference to
find new options.

## Modules and artifacts

### Build requirements

The Fabric build selects the Loom snapshot channel for the development
Minecraft target in the version catalog. This is a changing dependency: an
offline build validates the cached plugin, while a fresh online build may resolve
a different snapshot. Record the resolved Loom version when reporting build
problems; changing the Minecraft target requires revalidating both adapters.

Run the checked-in wrapper with a JDK matching `javaBuild` in the
version catalog:

``` shell
java -version
./gradlew build
```

Before starting the build, `java -version` and `./gradlew --version`
must report a launcher and daemon JVM compatible with `javaBuild`.
Gradle selects the compiler from `javaBuild`, while `javaTarget`
independently controls the generated bytecode. A lower target is not a
reason to run Gradle or the compiler with an older JDK. Do not switch to
an older JDK or Gradle release as a troubleshooting step unless a
concrete, reproduced incompatibility requires it and the reason is
documented.

The shared core, API and helper modules are build-time components. The
end-user Paper and Fabric JARs are written to `target/`:

``` text
AirMap-<version>+<rev>-paper.jar
AirMap-<version>+<rev>-fabric.jar
```

`<rev>` is Git's short form of the current commit. Builds with staged,
unstaged, or untracked files append `-dirty` after the revision. The
AirMap product version remains defined exclusively in
`gradle/libs.versions.toml`.

## World identity and storage

World configuration uses canonical Minecraft registry IDs without a
leading slash, for example `minecraft:overworld`,
`minecraft:the_nether` and `minecraft:the_end`. Mod dimensions retain
their complete namespace and path.

Historical names such as `world`, `DIM-1` and `DIM1` are accepted as
compatibility aliases. Storage uses a separate, filesystem-safe ID;
integrations must not derive paths from `DynmapWorld#getName()` or depend
on the storage-ID encoding.

File-tree storage migrates a single unambiguous legacy world directory to
the storage-safe ID without overwriting existing data. If multiple legacy
directories match, AirMap reports the ambiguity and does not migrate them
automatically.

## Web Chat Boundary

Browser-to-server web chat is disabled in this fork. The web UI message
display remains enabled: `chat`, `chatbox`, and `chatballoon` client
components are still used for server-to-web messages, join/quit notices,
player chat display, and map chat balloons. Do not remove those
components when disabling browser chat input. Marker popups and labels
are handled separately by the marker component and marker JSON files.

## JDBC Drivers

Database storage classes for MySQL and MariaDB are present. The
centrally selected MariaDB Connector/J is included as an extracted
driver resource. Dynmap first checks whether the configured driver is
already available on the server classpath. Otherwise, configure
`storage/driver-jar` and optionally `storage/driver-class`; the same
mechanism can load a separately supplied MySQL Connector/J.

## External Web Server and Live Data URLs

This fork keeps the existing Dynmap-style external web server workflow
intact. The generated web UI reads live data through the URLs written to
`standalone/config.js`. By default, those URLs point to the generated
standalone JSON files:

``` yaml
url:
    # configuration: "standalone/dynmap_config.json?_={timestamp}"
    # update: "standalone/dynmap_{world}.json?_={timestamp}"
```

Existing configuration remains supported, but deployments that directly
reference historical world-derived filenames or tile directories must
account for the storage-ID migration. Advanced deployments that route
live data through a reverse proxy or another endpoint can override these
URLs in `configuration.yaml`:

``` yaml
url:
    configuration: "up/configuration"
    update: "up/world/{world}/{timestamp}"
```

This is the supported compatibility path for custom routing. The project
should not require users to rebuild a working Nginx, Apache, or CDN
setup just to follow the fork. If a deployment serves the web UI from
one machine while the backend writes live JSON over NFS or another
shared filesystem, short-lived `404` responses for live JSON usually
indicate infrastructure timing or cache visibility issues. In that case,
prefer local filesystem/NFS/Nginx tuning or URL overrides over changing
the global project defaults.

In generated live-data URLs, `{world}` is a transport placeholder
supplied by Dynmap. External rules should pass it through unchanged and
must not assume that it is the public canonical registry ID.

## Internal Webserver Storage Endpoints

The internal Java webserver still serves normal web assets directly from
`webpath`. For SQL-style storage, it also exposes optional
storage-backed endpoints so users can run MySQL/MariaDB without an
external PHP webserver and without exporting duplicate tile files.

This is a deliberate fork-level change from original Dynmap and is
controlled by:

``` yaml
webserver-storage-endpoints: true
```

When the internal webserver is enabled and the storage default URLs
would otherwise point at `standalone/*.php`, `standalone/config.js` is
generated with Java-backed routes:

``` yaml
configuration: "up/configuration"
update: "up/world/{world}/{timestamp}"
tiles: "storage/tiles/"
markers: "storage/markers/"
```

Those endpoints read through the existing `MapStorage` API:

-   live configuration and world updates from standalone storage
-   map tiles from storage by world and tile URI
-   marker JSON, marker icons, and player faces from storage

External deployments are kept compatible. If `disable-webserver: true`,
or if explicit `url:` values are configured, the original external URLs
remain in use, including the original SQL PHP endpoints such as
`standalone/MySQL_update.php` and `standalone/MySQL_tiles.php`.

## External PHP SQL Endpoints

The bundled MySQL standalone PHP endpoints are kept for external
Apache/Nginx/PHP deployments. MariaDB storage uses the same
MySQL-compatible endpoint names and request parameters:

``` text
standalone/MySQL_configuration.php
standalone/MySQL_update.php?world={world}&ts={timestamp}
standalone/MySQL_tiles.php?tile=
standalone/MySQL_markers.php?marker=
```

The PHP code uses modern PHP conventions with strict types, `__DIR__`
includes, typed helper functions, `http_response_code`, consistent JSON
error responses for JSON endpoints, prepared statements, `utf8mb4`, and
path validation. `MySQL_config.php` is still generated by Dynmap and
remains compatible with the original variable names.
